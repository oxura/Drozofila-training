**После потокового пилота: сначала улучшить адресацию**

Измерения: `results/stage8_pilot/summary.json` и `post_pilot_review.json`.
Дополнительная диагностика описательная, проведена после пилота. Она не
меняет веса и выбор кандидата; финальные тесты 16/32/64 не открывались.

**Что получилось**

Обычный GRU: 33.75% dev; GRU с ячейками: 33.61%; контроль близкого числа
параметров: 33.33%. Это три варианта по одному seed, поэтому различия в
доли процента не обосновывают устойчивое преимущество. У варианта с ячейками
чтение исходного значения даёт 13.33%, ранней записи — 21.67%, последней —
65.83%. Инженерный ориентир памяти не достигнут.

При отключении вклада ячеек точность slots составляет 34.03%. Пилот не
показал, что дополнительные ячейки полезны для конечного ответа. Сброс GRU
перед запросом снижает обычную модель до 10.28%, вариант slots — до 15.56%.
Основная зависимость готового решения остаётся в рекуррентном состоянии.

На самих учебных задачах выбранные checkpoint дают 48.21% для GRU и 38.33%
для slots. Модели ещё не решают надёжно даже учебный набор. Это совместимо
с проблемами представления, оптимизации или недостаточным бюджетом;
не доказывает нехватку нейронов. Увеличенный GRU в этом пилоте не помог.

**Что показали коэффициенты ячеек**

Нормированная энтропия адресов чтения — 0.850 из 1: чтение распределено
между несколькими ячейками. Средняя масса коэффициента нужной записи
в точном аффинном обновлении памяти — 0.03795, последней записи — 0.03781.
Средний gate записи на событии запроса — 0.512. Распределённое чтение и
запись во время запроса сами по себе не являются ошибками.

Эти коэффициенты не учитывают векторы значений и выходную проекцию;
они не измеряют смысловую правильность или причинную важность события.
Вместе с отсутствием потери качества при отключении памяти они дают
основание испытать более устойчивое представление имени для адресации.

**Следующий отдельный пилот, ещё не выполнен**

1. Сохранить текущий streaming-интерфейс, GRU, число ячеек, бюджет и данные
   для разработки. Менять один механизм: адрес чтения/записи получать из
   отдельного общего кодировщика имени. Сейчас оба адреса зависят от GRU,
   поэтому представление того же имени меняется вместе с предыдущей историей.
   Кодировщик остаётся обучаемым; программного назначения имени ячейке нет.
2. Сравнить текущие адреса, общий кодировщик имени и контроль ёмкости.
   До запуска зафиксировать новый протокол и версии исходников; этот пилот
   не дополнять задним числом. Не менять одновременно gates, loss и объём сети.
3. Если адресация не улучшается, отдельным следующим опытом проверить
   промежуточные учебные цели для чтения. Контроли получают те же метки;
   истинные состояния по-прежнему отсутствуют при свободном решении.
4. Подтверждение минимум на трёх seed и новых закрытых тестах проводить
   после появления содержательного выигрыша на dev. Не тратить эту проверку
   на выбор среди нынешних трёх почти одинаковых слабых результатов.

Это продолжает первый пункт ROADMAP_BROAD_INTELLIGENCE.md. Затем — общий
повторяемый вычислительный шаг и выученная остановка. Подача конечного числа
WRITE-событий текущему пилоту не доказывает, что сеть умеет сама выбирать
длину вычисления. До замены основной модели необходимы проверки арифметики,
логики, переноса и сохранения прежних навыков.

Рост биологической графовой ветви 256 → 512 → 1024 и перестройка её рёбер
остаются отдельными сравнениями с продолжением малой сети и большой сетью
с начала обучения. Этот пилот не даёт основания утверждать пользу такого роста.

Для проверки сохранённого пилота без подстановки правильных ответов:

```bash
python fly_stream_memory.py 'код a=2;b=3;c=0;d=1;a=7;b=8;?a' \
  --checkpoint results/stage8_pilot/gru_seed0/best.pt --json
```

Его ответы могут быть неверны. Основная модель `fly_memory.py` и её выбор
